The study in one minute

A request can die in silence. The fix is a timer.

What happened
A parent started the entry form an hour early, from the car. She still stood in the rain at the gate for twenty minutes, and got in only when her son walked out and a guard phoned someone.
The real problem
Not the form. After you submit, nobody owns the request, nothing times out, and there is no fallback. If the approver ignores it, it is quietly cancelled and you start again.
What I proposed
Submit from anywhere with five fields. The system picks the approver. You can see who has your request. If nobody answers in 30 minutes, it moves to a backup by itself.
What I designed
Sixteen wireframes, a heuristic inspection that changed three things, and a clickable prototype in Figma. Jump to the design.

Phase 1 · The system today

Six screens at a gate with no signal

Every visitor fills in a third-party check-in form at the gate, then waits for someone to approve it before a pass arrives on WhatsApp. Four things break it:

  • No signal. There is no mobile data at the gate, and campus WiFi needs a coupon you can only get from inside.
  • No option for parents. “Purpose of visit” has four choices and none fits, then it demands a company name.
  • You must guess the approver. Approval moved from teachers to a few administrators. The form still accepts the wrong name without an error.
  • No time limit. An ignored request is never rejected. It is held, then silently cancelled.

The six screens below are the existing third-party system, captured as evidence. My proposed design is in Phase 4.

Phase 1 · User stories

Five things a visitor needs

  1. See whether my request has been opened, and who has it, so I know whether to keep waiting.
  2. Have it move to a backup approver if nobody responds in time, so one absent person can’t strand me.
  3. Let my host raise the request in advance from campus, so I never need data at the gate. The host raises it. Approval stays with the institution.
  4. Have the system work out the approver, so I never guess a name.
  5. Give only what the gate register uses, so I’m not asked for a selfie and ID digits for nothing.

Phase 2 · Information architecture · Card sort

People already think in “the state of my request”

Eight people sorted twenty features into six groups, or none, and could propose their own groups. Three results mattered:

  1. Status is one clear idea

    “Has my request been opened” and “how long does a decision take” were grouped together by all eight. The idea is in people’s heads and missing from the product.

  2. The fix had no home

    “Pass to a backup person after a set time” scattered across four groups. Nobody had used a system that does it. Yet one participant invented it unprompted:

    Time to respond. After which the visitor can seek help.

    Card-sort participant

  3. A majority can hide confusion

    “Add another visitor” won 5 of 8 votes, and was also named the hardest card to place. The numbers alone would have called it settled.

Two more results: visitors and hosts want opposite things, and my survey had a flaw

Visitor versus host. The parent wants less data collected. A student host asked for more, including a visitor photo and vehicle number. The visitor pays the privacy cost and gets no security benefit, so I sided with the gate register: five fields.

No “not sure” option. One participant pointed out that “doesn’t fit” was doing double duty as “I don’t know”. Fair. The tree test settled it by watching behaviour instead.

Phase 3 · Prioritisation (MoSCoW)

Four must-haves, no more

  1. Submit from anywhere, with five fields. A public link, not just a QR code at the gate. Only what the register uses.
  2. The system picks the approver. Based on who you’re visiting. You never type a name.
  3. You can see the status. Opened or not, and who has it.
  4. Timed hand-off to a backup. The only feature that touches the low point. The others make the wait visible; this one makes it end.

Should have

Host registers a guest · digital entry pass · decision alert · reminder to approver · add a visitor · gate desk number · offline pass

Could have

Reuse last visit · visiting hours · gate directions · exit pass · guests expected today · typical decision time · time slots · privacy notice

Won’t have, and why

Selfie, ID digits, vehicle number
The gate doesn’t use them, and data you collect can’t be un-collected.
Students approving their own visitors
The university just narrowed approval on purpose. A feature that reverses that gets rejected, not adopted.
Emergency button
With no set responder or time limit, it’s another silent queue.
In-app chat with the host
It competes with WhatsApp, and a visitor with no insider has nobody to message.

The hand-off is a timer and a rule over data that already exists, and it automates what guards already do by phone. Pre-registration needs student logins and a new user role, and most of its value (starting before the gate) already comes from the public link. Nothing except a time limit stops a request dying in silence.

The four must-haves, as screens

2. Heuristic inspection

I checked the first sketches against Nielsen’s ten heuristics. Three failed, and each one would have rebuilt a problem the research had found.

Visibility of system status

SketchThe status just said “Pending approval”. That is the exact silence this study is about.

WireframeThree named stages, who holds the request, minutes until it moves on, and a “last updated” time so an offline screen can’t pass for live.

User control and freedom

SketchOnce the form started, the only button was Continue.

WireframeBack on every screen, “Cancel and return home” on each form step, and a leave dialog that says your details stay saved.

Error prevention

SketchStep 2 had a free-text “Approver name” field, the exact mistake that stranded the parent.

WireframeIt asks who you’re visiting instead, adds a review step before sending, and a “no match” state explains why and offers other ways to search.

Reflection

What this would have meant for her

  • No professor’s name to guess, and no Aadhaar digits
  • She would have seen her request was waiting, and on whom
  • At 30 minutes it would have moved on by itself, instead of being cancelled while she stood in the rain

What I’d do differently

  • Write the proto-persona before interviewing. Mine was written after, so I can’t prove the order.
  • Add a “not sure” option to the card sort. A participant was right about that.
  • Recruit a real parent for testing. Every tree tester was a student.
  • Usability-test the prototype next, starting with the eight-item “Checking on My Request” section.
